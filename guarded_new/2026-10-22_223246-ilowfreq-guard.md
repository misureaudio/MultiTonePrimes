# `--ilowfreq` Range Guard Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** Make out-of-range `--ilowfreq` values fail fast with a clear, actionable error instead of silently mis-slicing (values ≤ 0) or crashing with a raw `IndexError` (values > N), across all three optimizer entry points.

**Architecture:** One shared validation helper in `multitone/optimizer.py` (the module both GPU scripts already import from), called in each `optimize*()` function immediately after the existing `load_attenuation()` call. The valid range is **dynamic** — it is `1..N` where N is the length of the frequency array actually loaded from the `multitone/data/*.mat` files for the chosen `--fraction`/`--fsam` — so validation happens at load time, not argparse time.

**Tech Stack:** Python 3, argparse, scipy.io (existing), no new dependencies.

---

## Context / assumptions

- `--ilowfreq` is 1-indexed (MATLAB style). The code does `slice_start = ilowfreq - 1` then `FrqPriLst_full[slice_start:]`:
  - `optimizer.py:205-211` (`optimize`)
  - `optimizer_gpu.py:66-69` (`optimize_gpu`)
  - `optimizer_gpu_Cl1_Gv2.py:66-69` (`optimize_gpu`)
- Current failure modes (verified by reading the code):
  - `ilowfreq ≤ 0` → negative `slice_start` → Python negative indexing → **silent** wrong slice (e.g. `0` → last element only, a 1-tone signal).
  - `ilowfreq > N` → empty slice → `lfl = int(FrqPriLst[0])` → **IndexError traceback**.
- N (length of the full frequency array) per (fraction, fsam), measured from the data files:

  | frac \ fsam | 44100 | 48000 | 88200 | 96000 | 176400 | 192000 |
  |---|---|---|---|---|---|---|
  | 3  | 30  | 30  | 34  | 34  | 37  | 37  |
  | 6  | 59  | 60  | 66  | 66  | 72  | 72  |
  | 12 | 106 | 109 | 121 | 121 | 131 | 133 |

  The table is for documentation/verification only — **not** hardcoded (the .mat files are the source of truth).
- `load_attenuation()` (already present in all three code paths) exits with `print(..., file=sys.stderr); sys.exit(1)` when the data file or the (fraction, fsam) variable is missing. The guard follows the same error style.
- `producer.py` takes **no** `--ilowfreq` (it reads the already-sliced list from the phase .mat) — no change needed there.
- `analyze_multitone_v0.py` does not reference `ilowfreq` — no change needed.
- `multitone/` has no test infrastructure (no `tests/`, no conftest). Verification below is CLI-probe based; an optional pytest task is included at the end if the user wants a permanent regression test.
- Interpreter for all verification: `D:\Source\hermes-dir\.venv\Scripts\python.exe` (workspace venv, per standing rule), run from `D:\Source\hermes-dir`.

## Design decision (recorded for the user's later review)

**Chosen:** dynamic validation after the .mat load.
**Rejected alternative:** a static `choices=` table of (fraction, fsam)→N in argparse.
Why rejected: (a) it duplicates the data files as a second source of truth that can go stale; (b) argparse cannot express a range that depends on two *other* arguments; (c) the .mat files are tiny and are loaded on every run anyway, so dynamic checking is free.
**Tradeoff:** the error fires after the .mat load (a few ms), not at parse time — acceptable, and it composes with the existing "file/variable not found" error path.

```python
def validate_ilowfreq(ilowfreq: int, n_freqs: int, fraction: int, fsam: int) -> None:
    """
    Validate the 1-indexed (MATLAB-style) low-frequency start index against
    the loaded frequency array length.

    Exits with status 1 and a clear message if ilowfreq is outside 1..n_freqs.
    """
    if not 1 <= ilowfreq <= n_freqs:
        print(
            f"ERROR: --ilowfreq={ilowfreq} out of range for "
            f"Fraction={fraction}, Fs={fsam}: valid range is 1..{n_freqs} "
            f"(1-indexed, MATLAB style).",
            file=sys.stderr,
        )
        sys.exit(1)
```

## Verification summary

1. Invalid probes (`0`, negative, `N+1`) on all three scripts → stderr message with the exact valid range, exit code 1, no traceback.
2. Boundary probes (`1` and `N` per a sample of (fraction, fsam) combos) → run to completion, exit 0.
3. Default invocation unchanged: `python -m multitone.optimizer --maxiter 1` (default `--ilowfreq 4`) → works exactly as before.
4. GPU fallback path (CuPy absent) still guarded via the CPU path.

## Risks, tradeoffs, open questions

- **Behavior change (intended):** `--ilowfreq 0` previously produced a silent 1-tone signal (negative-index slice); `> N` produced a traceback. Both now exit 1 cleanly. Anyone scripting against the old bug would notice — expected and desirable.
- **Error fires post-load:** the .mat is loaded before the range check (a few ms). Accepted tradeoff for not duplicating the N table. If the user prefers parse-time failure, the alternative is a static (fraction, fsam)→N table in `main()` — rejected here, but a 10-line change if wanted.
- **Helper error style:** uses `sys.exit(1)` to match `load_attenuation`. Alternative: raise `ValueError` and catch in `main()` — more idiomatic for library code, but diverges from the module's existing convention. Open for the user to pick.
- **`ilowfreq = N`** (single tone) is accepted as valid; it is degenerate but legal MATLAB behavior. If the user wants a minimum tone count (e.g. `ilowfreq ≤ N-1`), that is a one-line change in the helper.
- **No lock on the data files:** if the .mat files are ever regenerated with different lengths, the guard tracks them automatically (that is the point of the dynamic design).
